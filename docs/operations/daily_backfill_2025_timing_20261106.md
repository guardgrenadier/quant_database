# 2025 年回填耗时诊断（2026-11-06）

结论：**主要成本是串行请求的固定启动间隔，以及全年指数的大范围检查引用关联 SQL；实际发布事务占比很小。** 本次只统计和做只读对照，没有修改生产 SQL、限频、业务规则或数据。

**后续实现更新：** 用户确认优化后，正式审计 SQL 已改为按展开 Unit 键关联；用户确认 10,000 积分后，七项日频间隔已从 1.3 秒降为 0.13 秒。完整验证和新运行观测见[优化记录](ingestion_performance_optimization_20261106.md)。本页其余数字描述优化前的诊断样本。

## 统计范围及口径

样本为诊断暂停前已完成并复核的 **48 个 Run、1,714 次请求**：全年指数一次；六项股票日频的 12～6 月，以及 5 月已完成的前五项。样本审计窗口约 55.2 分钟，Run 业务阶段累计约 48.5 分钟。

数据来自 meta.run.started_at／finished_at、request_attempt.requested_at／elapsed_seconds、publication.published_at 和运维摘要。published_at 为发布事务时间，标记事务起点，不等于每条 INSERT 的结束时间。

| 环节 | 累计耗时 | 说明 |
|---|---:|---|
| 依赖／Scope 至首个请求 | 7.7 秒 | 不含 CLI 导入和初始化 |
| 请求计时器 elapsed 累计 | **13.6 分钟** | HTTP 往返、响应读取和协议解析，非纯网络时间 |
| 请求之间的空档 | **26.2 分钟** | 主要为 1.3 秒启动间隔，另含证据写入、逐页转换及计时边界差异 |
| 最后请求结束至发布事务开始 | **8.1 分钟** | 获取尾部、集中准备、验证及检查审计等 |
| 发布事务至 Run 收尾 | **25.5 秒** | 发布和结束审计合计 |
| Run 之间的间隔 | **约 6.7 分钟** | CLI 进退、运维复核、dbt、调度间隔，不能全算为 dbt |

上表不包括首轮预检／备份，也不包括这次诊断暂停。首轮 prepare.py 创建到 baseline.json 完成约 46.9 秒，包含预检、全表摘要、备份及校验，是文件时间推算，不能进一步当作独立复制耗时。

**计时限制：** 现有日志没有 prepare、validate、record_checks 等独立阶段计时。控制器单调时钟和审计墙钟存在差异：指数 CLI 摘要为 794.2 秒，审计 Run 区间为 857.2 秒；部分股票 Run 也有较小差异。因此不将二者相减伪造启动／清理精确耗时，阶段表用于近似定位。HTTP elapsed 与请求时间戳之间的口径差异也包含在请求间空档里。

本次为读取审计，在当前命令自然结束后暂停调度，墙钟记录约 9.5 分钟；这段诊断开销单列，不计入上表。5 月 stk_limit 的监督器 seconds 受到暂停影响，已从诊断样本排除；其实际 Run 和请求审计不被改写。统计后已发送 SIGCONT 恢复原调度。

## 已验证的瓶颈

### 1. 固定 1.3 秒串行启动间隔

八成以上股票样本、指数约 95% 的相邻请求起点落在 1.28～1.40 秒区间，中位数约 1.3001 秒；源码在每次调用前 sleep 至 1.3 秒间隔。请求本身更快时，节约的时间会被等待吸收。

按已观察的分页量估算，六项股票日频每天约 9 次请求，243 日约 2,187 次；指数 267 次，全年合计约 2,454 次。73 个独立 Run 内至少约 2,381 个串行间隔，1.3 秒节奏给全年请求阶段设定约 **51.6 分钟**下限，尚未加审计、运维和慢请求额外成本。该下限已包含间隔内的请求执行时间，不能再把 HTTP 总时长完整叠加一次。

### 2. 年度指数的检查引用关联

core/audit.py 的 record_checks 先按 run_id 连接 Unit 与 Check，再用 list_contains(CAST(units AS VARCHAR[]), unit_key) 过滤。当前年度规模为 192,699 个 IN_SCOPE Unit、243 条局部检查，潜在候选关联约 **4,683 万对**，每对还需在 Unit 数组内查找。

在同一份真实年度数据上，只读查询测得：

| 查询 | 处理范围 | 墙钟耗时 |
|---|---|---:|
| 原关联表达式 | 1 个交易日 | 2.14 秒 |
| 原关联表达式 | 3 个交易日 | 5.16 秒 |
| 将检查 Unit 展开、去重后按键连接的只读原型 | 全年 192,699 个 Unit | **0.164 秒** |

原型保留全局检查分支和局部重复 Unit 去重，生成的全部 Unit.check_ids 与当前正式审计双向 EXCEPT ALL 差异为零。没有执行 UPDATE，也没有改动生产实现。原全年 SQL 未为诊断重复执行，不能直接宣称整个 468.71 秒都是该 SQL；只读样本和执行计划已明确支持它是首要本地优化目标。

### 3. 重复运维读取

一次全量 Serving 原行情双向对照实测约 10.06 秒、累计 CPU 约 235 秒（多核 CPU 时间，不是墙钟）。每月重复读取、逐项复核及 dbt 累计有成本，但命令间 6.7 分钟还包含 CLI 和调度，不能全部归到数据校验。

## 建议顺序

1. 优先局部优化 record_checks 的关联实现，保留全局／局部、去重、未知归属和审计引用语义，并验证对应边界；不取消审计。
2. 保留核查职责，合并运维重复读取，统一单调时钟阶段计时，以轻量日志记录，不新增 Meta 共享字段或业务快照。
3. 核实实际账号及接口配额后再评估 1.3 秒参数或请求编排；仅把月命令合并为年命令不会减少六项逐日请求量。
