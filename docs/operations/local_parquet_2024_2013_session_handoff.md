## 1. 当前实际状态

本次只执行了 2024 年，没有进入 2023～2013，也没有修复 2025 既有失败或重跑 2013-01-04。

2024 年 242 个开市日全部各执行一个本地 Parquet CLI Run，全部为 PARTIAL：预期 1,296,795 Unit，成功发布 1,288,980 Unit，保留 7,815 个 FAILED Unit；新增 Canonical 310,711,721 行。当前全库分钟共 719,873,779 行。成功 Unit 的 Publication、Coverage、行数、依赖和源身份逐日核对一致；失败 Unit 未发布，不能将本年被描述为所有 Unit 完整覆盖。

年度范围、版本、旧事实和旧 Meta 审计已通过。13 张其他 Canonical、全部旧 Meta、既有分钟逐月双向比较均为零差异。没有 RUNNING Run、WAL 或后台任务。

主库 `data/warehouse.duckdb` 当前 30,058,491,904 字节。唯一已验证恢复点仍是批前文件 `data/backups/warehouse-20261111T005508+0800-after-suspension-format-repair.duckdb`，SHA-256 `2bb42b6108ee0a0a63ffb9ddf5b779a4fd26b9f331bbbded1d984f4b88fbd227`。**年度后恢复点没有轮换，因此当前 2024 新增数据没有新的全文件恢复点。**

C 盘可用空间从本 session 开始时约 44 GiB 降至当前约 33 GiB。若按现有方式复制年度后恢复点并仍保留 20 GiB 余量，还差约 14.6 GiB，故停止轮换和下一年度。D 盘约 62 GiB 可用，但未获授权把恢复点移到 D 盘。

## 2. 为什么整体很慢

回填本身逐日耗时合计 6,063.05 秒，约 101 分钟；单日通常 23～29 秒，集中缺源日约 13～26 秒。最大 RSS 3,770,820 KiB。主要成本不是网络下载，而是每个自然日都重新启动正式 CLI，读取并哈希整份日 Parquet，在单内存批次中转换约 120～130 万条 Raw，构造并验收约 5,300 个股票日 Unit，再执行 DuckDB 发布、检查点和当日只读审计。全年 242 个独立进程，不能并行或合并 Run。

每日辅助审计还重新计算源文件完整 SHA-256，并检查 Unit、Publication、Coverage、逐 Unit 行数、依赖和检查规则。这增加了 I/O 和 SQL 成本，但当时用于落实用户要求的逐日身份与发布一致性证明。

年度末旧数据审计又耗时 3,925.56 秒，约 65 分钟。它使用单线程、2 GiB 内存限制和分片，并非整年分钟一次性比较；但逐表、逐月双向 `EXCEPT ALL` 仍需扫描大量数据。

本 session 没有使用 `--keep-artifacts`，避免导出整张 Canonical 和全阶段快照。后续优化应先区分“正式 CLI 转换/发布耗时”和“Agent 辅助审计耗时”，再讨论哪些证明可以复用，不能为提速直接削弱契约。

## 3. 为什么检查了 2025 和 2026

没有重新回填或修复 2025/2026。2025 全年及 2026 既有分钟出现在年度审计中，是因为运行手册要求把批前恢复点中的既有分钟与当前库做旧事实保护对照，防止新写 2024 时意外改写旧数据。

审计按 2013-01、2025 的 12 个月、2026-01/02/03/04/10 分片，双向差异均为零。这是有意执行的旧数据保护，不是误进入 2025 年度任务。fresh session 可以讨论该证明的更高效实现，但本次没有自行省略。

## 4. 遇到的质量问题和政策变化

最初授权路径误写为 `/mnt/d/BNetdiskDownload/stock_1min`，随后用户确认正确路径为 `/mnt/d/BaiduNetdiskDownload/stock_1min`。

2024-01-02 有 239 个北交所 `daily_conflict` 和 `302132.SZ` 一个同类错误，首次因集中模式停止。01-03 又出现 239 个北交所 `auction_not_reported`，并再次出现 `302132.SZ`，按原政策停止。用户随后明确：已登记 Unit 级质量规则即使集中或连续出现，也先记录并推进，全部历史结束后统一处理。该政策只改变日期间继续条件，没有放宽 Validator 或允许失败 Unit 发布。

全年失败规则汇总：`local.daily_conflict` 5,751、`local.auction_not_reported` 1,997、`local.empty_ambiguous` 66、`local.volume_amount` 1。高频包括 `302132.SZ` 242 次、`920174.BJ` 39 次、`920964.BJ` 34 次，以及多组北交所集中缺源/竞价缺失。逐日代码、Run ID、Coverage 和旧成功版本记录见主回填日志及审计 JSONL。

## 5. 执行辅助程序的问题

生产代码、Schema 和业务契约未修改。为减少手工执行，我在 Bash 中使用了内联串行调用与只读审计辅助程序，出现三次辅助写法错误：磁盘字典误迭代键、JSON 提取比较缺括号、耗时 `0:25.39` 误按整数解析。

第一次发生在首日启动前；后一次发生在 2024-01-03 CLI 已正常结束之后。均没有重复运行既有日期，也没有因此重跑 PARTIAL。2024-01-03 随后由独立只读查询完成审计。修正后剩余日期连续执行完成。年度审计临时值列表另有一次 SQL 参数写法错误，修正后查询通过，不影响数据库。

这些事件说明辅助编排也需要更稳定、输出更短的固定工具，而不是在多次等待中反复携带长内联程序。

## 6. 为什么本 session 上下文占用很高

用户观察到上下文已占用约 80%。主要原因是目标模式进行了 100 多次连续 turn；每次等待后台任务都返回了完整内联 Bash 程序和较长输出，月度又记录了大表，加上多次政策修订和逐日进度消息。数据库内存 RSS 与会话上下文占用是不同概念，不能把二者混淆。

fresh session 不应继承这种高输出执行方式。可讨论使用固定、简短、可恢复的外部执行记录和精简任务输出，同时保留库内 Meta 作为正式审计。
