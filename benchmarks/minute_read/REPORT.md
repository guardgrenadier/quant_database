# 分钟数据读取基准:原始 Parquet 视图 vs 标准化 Parquet vs DuckDB 表

日期:2026-09-21。纯实验,未改动正式数据与生产代码。可复现脚本:`bench.py`;原始测量:`results.jsonl`;运行日志:`full_run.log`。

## 环境

- WSL2 (Linux 6.6, x86_64),32 核,15GB 内存 + 4GB swap。
- 数据位于 WSL Linux ext4 虚拟盘(/dev/sdd,非 Windows 挂载盘),测试前可用空间约 950GB。
- Python 3.12.3,DuckDB 1.5.5,pyarrow 25.0.1,pandas 3.0.6。
- 固定设置:所有版本/任务均 `threads=16`、`memory_limit='6GB'`、固定 temp 目录;测试期间无并发基准任务。

## 数据概况(原始 Parquet)

- 路径 `data/raw/stock_1min/year=YYYY/YYYYMMDD.parquet`,2010–2026(2026 不全),每天一个文件,约 1.2M 行/天。
- schema 全年份一致:`code/trade_time/date` 为字符串,OHLC/`vol`/`amount`/`pre_close`/`change`/`pct_chg` 为 FLOAT(float32),另有 `__index_level_0__` BIGINT。
- Snappy 压缩,每文件约 2 个 row group(各约 1M 行 / 20MB)。
- `trade_time` 格式 `'YYYY-MM-DD HH:MM:SS'`(长度恒 19);`date` 为 `'YYYYMMDD'` 字符串(与 trade_time 不同格式,是真实转换需求)。
- 文件内基本按 (code, trade_time) 排序(抽查 123 万行仅 1 处逆序)。09:30 是真实时间标签 bar(09:30–15:00 共 241 个标签/天),按标签过滤,未用"删首条"代替。
- 实验范围:1m=2025-01(23.4M 行),1y=2025(316.4M),2y=2024–25(627.7M),3y=2023–25(928.1M 行,原始压缩约 14.8GB)。

## 三个版本(语义一致,已验证)

统一输出列:`symbol VARCHAR, trade_date DATE, bar_time TIMESTAMP, open/high/low/close/vol/amount FLOAT`(源即 float32,精度无额外需求,未做无谓转换)。

- A 原始视图:查询时 `code AS symbol`、`CAST(trade_time AS TIMESTAMP)`、`::DATE` 生成 trade_date、`bar_time::TIME <> 09:30` 过滤。
- B 标准 Parquet:转换结果按"每天一文件"镜像原布局预写,Snappy、默认 row_group_size=122880、无 ORDER BY(保持原始自然序,未做布局优化)。
- C DuckDB 表:同一结果 CTAS 进单一 `bars` 表(每个范围单独建库)。

一致性:三个版本在 1m 和 3y 上行数、日期/时间边界、证券数、各列和(浮点相对容差 1e-6,仅为扫描顺序舍入差)完全一致;首个交易日双向 EXCEPT ALL 差集均为 0。EXPLAIN ANALYZE 确认 A 的 CAST/生成列/过滤在任务 1 中真实执行(`explain_analyze_A_1m.txt`)。

## 转换成本拆解(1 个月原始 Parquet,中位数)

| 步骤(累积) | 中位数 s | 本步增量 |
|---|---:|---:|
| 1 读取所需源字段 | 0.115 | — |
| 2 重命名 | 0.110 | ~0(DuckDB 别名无成本) |
| 3 trade_time→TIMESTAMP | 0.296 | **+0.186** |
| 4 生成 trade_date | 0.324 | +0.028 |
| 5 过滤 09:30 | 0.375 | +0.051 |

转换总成本约 0.26s/月,其中字符串→TIMESTAMP 解析占约 70%,生成日期列与过滤各占 ~10–20%;重命名与数值列(float32→float32,无转换)基本免费。

## 回答实验问题

1. **实时清洗增加多少,耗在哪**:3y 聚合扫描 A 比 B 慢 5.6s、比 C 慢 4.2s(约 1.9x);全列 Arrow 导出差距放大到 75s/59s。增量主要来自 trade_time 字符串→TIMESTAMP 解析(~70%)。
2. **B vs C 差距**:B 一致略快(3y 扫描快 1.4s、Arrow 快 16s)且体积更小(12.8 vs 19.9GB)。差距存在但不悬殊。
3. **2–3 年可接受性**:SQL 聚合扫描全部版本 4–12s,可接受;Arrow 全量消费 90–166s,适合批处理不适合交互;pandas 全市场 2–3 年(~53GB)超出本机内存,不可行,需按年/按批处理。
4. **两个 10 秒指标(3y,分开报告)**:
   - "额外耗时 ≤10s":聚合扫描 A−B=5.6s、A−C=4.2s,**达标**;Arrow 导出 A−B=75s,**不达标**。
   - "总耗时 ≤10s":聚合扫描 A=11.9s,**略超不达标**(B=6.3s、C=7.7s 达标);Arrow 导出全部版本(90–166s)**均不达标**。
5. **实测 vs 外推**:扫描与 Arrow 的 1m/1y/2y/3y 全部实测;pandas 仅 1m 实测,其余为标注外推。缓存状态未控制(未清系统缓存,B/C 构建后即测,首跑列仅供参考,不能视为冷盘性能)。RSS 为进程峰值上限。

## 结论(以绝对耗时为主)

- 对"全市场 2–3 年聚合扫描"这类任务,原始 Parquet + 实时视图的代价约为每次查询多 4–6 秒(总计 ~12 秒)。若这类查询低频执行,可以不建标准化层;若交互式反复使用,标准化 Parquet 把每次扫描压到 ~6 秒,值得一次性的 216s/12.8GB 构建成本。
- 对"全列导出到 Python"类任务,三版本都远超 10 秒(1.5–3 分钟),实时转换额外增加约 1 分钟;此场景下标准化收益更大,且应考虑列裁剪而非全列导出。
- DuckDB 实体表在本实验中没有任何读取速度优势且占空间更多,其价值在索引/更新/事务等场景,而非全表扫描。
