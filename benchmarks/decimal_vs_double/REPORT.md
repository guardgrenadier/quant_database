# 价格类型 A/B:DOUBLE vs DECIMAL(18,6)

日期:2026-09-21。纯实验,未改动正式数据。脚本 `bench.py`,原始测量 `results.jsonl`,日志 `full_run.log`。
环境同前次基准:WSL2 ext4,32 核,15GB 内存,DuckDB 1.5.5 / Python 3.12.3,固定 threads=16、memory_limit=6GB;缓存状态未控制(首跑列仅供参考)。

两版本除 OHLC 类型外完全一致:`symbol VARCHAR, trade_date DATE, bar_time TIMESTAMP, vol BIGINT, amount DECIMAL(18,4)`;同样按天一个 Parquet 文件、Snappy、默认 row group、无排序、无 pre_close/change/pct_chg。源价格本身为 float32(无原始数值文本可核对)。

## 0. 构建时发现的关键坑(必须先记录)

**DuckDB 1.5.5 直接 `CAST(FLOAT AS DECIMAL(18,6))` 是有损且错误的**:`CAST(1501.0::FLOAT AS DECIMAL(18,6))` 得到 `1500.999936`(1501.0 在 float32 中精确存在)。必须经 DOUBLE 中转:`CAST(CAST(x AS DOUBLE) AS DECIMAL(18,6))` 得 `1501.000000`。本实验 B 版本用后者构建;任何正式 ingestion 若写 Decimal 也必须走 DOUBLE 中转。

## 1. 正确性核对(1 个月,23,418,210 行)

- 行数、空值(0)、主键 (symbol, bar_time) 重复(0):两版完全一致;无 Decimal 溢出。
- 经 DOUBLE 中转后,DOUBLE 与 DECIMAL 转回 DOUBLE 的**最大绝对差 = 4.93e-7**(恰为第 6 位小数舍入半格 5e-7 以内)。
- 有差记录 23,215,893 行(占 99%),但全部是**二进制浮点表示噪声**(如 float32 的 160.99 实际存储为 160.99000549316406,DECIMAL 量化其精确二进制值到 160.990005),不是有效行情精度损失。A 股最小价位 0.01,差值比它小 4 个数量级。
- 真正的精度瓶颈是**源数据 float32**(其自身与预期十进制价格的偏差可达 ~1e-5 量级),DOUBLE 和 DECIMAL 都原样继承;DECIMAL(18,6) 不能"恢复"tick 价格,只是把 float32 噪声量化到 6 位小数。

## 3. 精确性小实验(1 个月真实数据)

- `high = close` 判等:两版各 550,651 行,**判定不同的行数 = 0**(在 float32 源精度下,相等性判定完全一致)。
- `close - open`:两版最大绝对差 9.9e-7。
- 日内价格差累计(按证券-日 sum(close-open)):两版最大差 2.1e-5(一个月 131 万个证券-日上的最大值,约为 2 个 tick 的千分之一)。
- 日频特征最大差:振幅均值 7.0e-8,实体收益均值 1.2e-8——对任何统计研究都不可感知。
- 附带观察:本工具链(DuckDB 1.5.5)中不显式转换直接 `fetchdf`,DECIMAL 列也会得到 float64;但 Arrow 分批路径下 Decimal 是 decimal128,正式比较仍以显式 CAST 后输出 float64 为准(本实验做法)。

结论:你的下游用法(振幅、收益等最终都进入浮点统计)**不需要精确十进制运算**;Decimal 的"精确"体现在存储口径(固定 6 位小数十进制语义、价格差精确到 1e-6),而不是让百分比计算更准。

## 4. 按既定决策顺序的结论

先看 3y 的导出 float64 和日频特征,再看文件大小:

1. **导出 float64:Decimal 慢 26.4s(62.9s vs 36.5s,1.72x)**,差距远超测试波动(±2s),出现在每次全量导出;全市场数据进 pandas/NumPy 是研究端高频动作,这是最重的一票。
2. **日频特征:Decimal 慢 0.7s(+11%)**,可忽略。
3. **文件大小:基本相等**(−0.8%)。
4. 额外信息:库内纯扫描 Decimal 反而快 5.2s(INT64 缩放整数聚合比浮点聚合更易向量化),若工作负载以库内 min/max/sum 为主,这一项会反转结论。

**建议:保持 DOUBLE。** 理由:(a) 源数据已是 float32,Decimal 并不能获得真正的 tick 级精确口径,只是把浮点噪声量化到 6 位小数;(b) 精确性实验显示两类任务的结果差异 ≤1e-7,不影响任何研究结论;(c) 你最看重的导出路径上 Decimal 每次全量导出多付 ~26s;(d) DuckDB 直转 FLOAT→DECIMAL 有 bug 需 DOUBLE 中转,增加 ingestion 复杂度。若未来源数据升级为精确十进制文本(如交易所原始行情),或出现对价格差精确性敏感的需求(逐 tick 对账),再按本脚本重测即可——届时 Decimal 的存储口径优势才是真实的。
